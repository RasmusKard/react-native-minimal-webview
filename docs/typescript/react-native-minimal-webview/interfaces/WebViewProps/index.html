WebViewProps¶

What the WebView loads, its settings, and the callbacks for its events and the page's requests.

The ones from React Native's ViewProps (style, testID, nativeID, the accessibility props, layout and touch events) go to the native view.

Every on… callback is read when its event or request comes, so adding, changing or removing one applies to the next, and a request without one gets the default described on its prop. One that answers a request and throws (or rejects) is logged with console.error and gives the refusing answer: onNavigationRequest block, onOpenExternal null (the core opens nothing), onFileRequest cancel, onPermissionRequest deny, an extension's onEvent null.

The signal such a callback gets aborts when native stops waiting for its answer (the page moved on, crashed or unmounted), and a late answer is dropped.

JS dialogs (alert, confirm, prompt) and HTTP auth have no prop. iOS shows a UIAlertController titled with the frame's host, one at a time (one that comes while another shows is cancelled), and Android WebView's own dialogs. An auth challenge is cancelled on Android, and gets WebKit's default handling on iOS: without a stored credential, the site's 401 page shows. dialogs and basicAuthCredential of @react-native-minimal-webview/extensions take them over, or a native hook does.

Properties¶

android?¶

optional android?: AndroidSettings

Android

Android settings by setter name; see AndroidSettings.

bridge?¶

optional bridge?: Bridge<BridgeMethodMap, BridgeEventMap>

The bridge to the page, from createBridge.

Read when the WebView is created: another bridge recreates it (the page reloads and the navigation state starts over), so make it once (useMemo). A bridge serves one mounted WebView at a time: attaching it to a second throws.

On Android with a WebView older than 101 there is no bridge: calls reject with unavailable, and a warning says so, once per process.

extensions?¶

optional extensions?: readonly (false | HookExtension | null | undefined)[]

The native hooks to turn on, as HookExtensions: a package with a native hook exports a function that returns one.

A false, null or undefined entry is left out, so on && extension(…) switches one on and off; see HookExtension.options for what off means. A hook attaches when its key first appears, and a later change of its options reaches it live, without recreating the WebView. A key turned on after the WebView was created attaches its hook then, unless the hook has a configure step or its own WebView class (webViewClass, webViewFactory): that one attaches only when the WebView is created, and a warning says so.

Native hooks guide

injectedScripts?¶

optional injectedScripts?: InjectedScript[]

Scripts to run at document start, before the page's own, in the frames picked by each script's allFrames and origins.

A change applies from the next navigation. On Android with a WebView older than 101 they don't run (a warning says so, once per process).

ios?¶

optional ios?: IOSSettings

iOS

WebKit settings by property name; see IOSSettings.

navigationRules?¶

optional navigationRules?: readonly NavigationRule[]

Which navigations load in place, open externally or are blocked, decided natively; the first matching rule wins, and with no match the navigation is blocked.

Unset, the rules are defaultNavigationRules; [] is no rules, so every navigation they decide is blocked.

about:, blob:, data: and javascript: always load in place.

The source load, reloads and back/forward skip the rules; a redirect of the source load doesn't, nor on Android a redirect of a reload or back/forward. The rules never see a form POST, on either platform: it loads in place, and one to a new window loads in place on iOS, and on Android isn't shown (the request may still reach the server).

An external intent: URL (Android) opens only as a browsable intent, without its explicit component or selector; when no app handles it, an http(s) S.browser_fallback_url goes through the rules (main frame, no user gesture), and the intent: itself is reported as block.

A change applies from the next navigation.

A native hook can take these decisions, defaults included: see WebViewContext.clients (Android) and navigationDelegates (iOS).

Example¶

<WebView
  source={{ uri: 'https://example.com' }}
  // myapp: opens externally even without a user gesture; everything else as by default
  navigationRules={[{ scheme: ['myapp'], action: 'external' }, ...defaultNavigationRules]}
/>

onDownload?¶

optional onDownload?: (result) => void

A download finished (Download) or failed (DownloadFailure).

With this prop the core saves the file: iOS downloads it in the page's session; Android fetches it again with the host's cookies (whatever their SameSite) and the page's user agent. That fetch sends no POST body, source headers or HTTP auth, so a download that needs them can fail, or save the server's login page as the file, and it fails above 100 MB, on a redirect off https, and for blob: on a WebView older than 83.

Without this prop, an http(s) download opens externally (onOpenExternal or the system browser, without the page's session), and a data: or blob: one is dropped. A PDF is a download on Android; iOS shows it inline.

On iOS a file response is a download only in the main frame; an <a download> link is one from any frame.

On Android a native hook's WebViewContext.onDownloadStart is offered each download first, and one it takes reaches neither this prop nor the external fallback.

onError?¶

optional onError?: (event) => void

A main-frame load failed, or got an HTTP error status.

After a failed load iOS keeps the page before it on screen, and Android shows WebView's own error page. On Android with a WebView older than 146, an SSL error on a back/forward load isn't reported.

A renderer crash isn't reported here: it makes the cut-off load's outcome failed and calls onProcessGone.

onFileRequest?¶

optional onFileRequest?: (request, signal) => string[] | Promise<string[] | null> | null

Android

Answers <input type="file"> with file:// or content:// URIs, or null to cancel.

Without it, the system file chooser opens, one at a time for the whole app, and ignores capture: a request while one is open is cancelled, and if the chooser's activity died without returning a result, so is every request until the app restarts.

iOS always shows WebKit's picker, which needs NSCameraUsageDescription and NSPhotoLibraryUsageDescription.

Until the answer settles, the page's next file request waits.

onNavigationRequest?¶

optional onNavigationRequest?: (request, signal) => NavigationAction | Promise<NavigationAction>

Decides each navigation an ask rule matches, within 1 s.

A late, missing or other answer is block, as is one still pending when another page commits; signal aborts at the timeout and at that commit. Without this prop, ask is block. Until the next commit, a URL it allowed isn't asked again on a redirect back to it (Android), or when the same kind of frame loads it again (iOS).

onOpenExternal?¶

optional onOpenExternal?: (request, signal) => boolean | void | Promise<boolean | void>

Opens external navigations, every one, an Android intent: URL included, before onNavigation reports them.

Return false (a promise is awaited) to hand it back: the core then opens it as it does without this prop, an intent:'s fallback URL included. Any other answer, undefined too, means you opened it. When signal aborts, nothing opens it.

Without this prop, the system browser or app for the URL opens it, without asking canOpenURL first, so no LSApplicationQueriesSchemes (iOS) or <queries> (Android) entries are needed.

onPermissionRequest?¶

optional onPermissionRequest?: (request, signal) => boolean | Promise<boolean>

Camera, microphone and, on Android, location and protected media (DRM) for the main frame.

Answer true to grant, having asked the OS first (expo-camera, expo-location): without OS permission the page's request fails anyway. On iOS, true also skips WebKit's own prompt.

Without this prop, Android denies and iOS shows WebKit's prompt (location always does). iOS needs NSCameraUsageDescription and NSMicrophoneUsageDescription, Android the CAMERA and RECORD_AUDIO manifest permissions. Android keeps a location answer until the page changes.

Anything but true denies. signal also aborts when Android withdraws the request. Until the answer settles, the page's next request of the same kind waits.

pullToRefresh?¶

optional pullToRefresh?: boolean = false

Pull down at the top of the page to reload: UIRefreshControl on iOS, SwipeRefreshLayout on Android, where a pull inside a scrolled inner scroller (overflow: auto) scrolls it instead.

It reloads as reload() does, a POST source included. A change applies at once.

ref?¶

optional ref?: Ref<WebViewRef>

Gets the WebViewRef.

Give each mounted WebView its own ref: one shared by two points at the last mounted (with a warning in development), and can turn null when either unmounts.

sharedCookies?¶

optional sharedCookies?: boolean = false

iOS

Copies HTTPCookieStorage (native requests) into the WebView before each source load, which waits for it, and the WebView's cookie changes, deletions included, back as they happen.

Android needs nothing: CookieManager is shared app-wide, and flushed when the app goes to the background.

source¶

source: WebViewSource

What to load.

A new source loads at once, unless it equals the loaded one field by field: that loads nothing, even after the page navigated away.

userAgent?¶

optional userAgent?: string

Replaces the whole user agent, over ios.webView.customUserAgent and android.settings.userAgentString. Without it, those keys apply; unset, they are the platform's own user agent.

To append to the default one instead, set ios.configuration.applicationNameForUserAgent and, on Android, android.settings.userAgentString to WebView.android.defaultUserAgent plus your suffix.

A change applies from the next navigation.
