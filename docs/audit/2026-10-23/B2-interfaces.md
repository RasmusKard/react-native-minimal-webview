### (a) Summary

1. The four surfaces keep their conventions: no stale or renamed name, 10 lowercase error codes, a discriminant wherever states differ, every TS platform-only item marked but `didCrash`; most of the 2026-10-21 interface work landed (api-surface 8 of 15 done, 4 kept; 5 of 9 extension seams).
2. Items: 2 interface bugs (Android `ref.hook` rejects the wrong code mid-rebuild; iOS `emit`/`ask` race off main where Kotlin hops), 1 silent setup error (a `hookOptions` key no hook claims), 3 accidental hooks asymmetries (`activity`, the detach reason, an ask after close), a wider public Kotlin surface; all S.
3. The rest is about 10 one-sentence doc fixes (A4's list, confirmed) and a keep on every untyped native boundary: the typed alternatives cost 3 to 150 lines and catch less than the vectors and the key test; only a TS hook registry (~30 lines) is cheaper than it looks.

## (b) Findings, ranked by impact

**B2-01 `ref.hook` while Android rebuilds a crashed WebView rejects `hook_not_handled`; the types promise `unavailable`.** types.ts:256-257 and props.md:31-33 list `hook` with `evaluate`/`get`/`call`. The `hook` function looks the handler up without checking `recovering` (MinimalWebViewModule.kt:148-150), and `processGone` → `detachHooks()` has emptied `hookContexts` (MinimalWebView.kt:361, 279), so `hookHandler` misses (:299); `get`/`call` check it (MinimalWebViewModule.kt:168-171), `evaluate` too (MinimalWebView.kt:349-350). A caller reads `hook_not_handled` as "not installed" and gives up. Q2. **simplify**: `if (view.recovering) return@AsyncFunction promise.reject("unavailable", RECOVERING, null)` before the lookup (1 line); CHANGELOG.md:45 adds `hook`. S, high. Breaks: nothing; no suite calls `hook` mid-rebuild. (A4-02)

**B2-02 iOS `context.emit`/`ask` run on the caller's thread; Kotlin's hop to main.** Hooks.swift:102-109 call the view directly, and `ask` writes `nextAskId` and `pendingAsks` (MinimalWebView+Navigation.swift:94-98), which `answer` and `cancelAsk` change on main (MinimalWebViewModule.swift:54-56; +Navigation.swift:101-105). Kotlin hops (Hooks.kt:119-122, 143-146). `WebViewContext` isn't `@MainActor` (Hooks.swift:50), so nothing flags a hook that emits from its own `URLSession` completion; native-hooks.md:69 says "Everything runs on the main thread", true of the core's callbacks only. Q2, Q4. **simplify**: the same `onMain` in `HookContext` (~4 lines); native-hooks.md:69: "`emit` and `ask` may be called from any thread; every callback runs on main". S, high. Breaks: nothing. (A4-05)

**B2-03 A `hookOptions` key no hook is registered under does nothing, silently.** Both platforms keep the hooks whose key is enabled (MinimalWebView.swift:214; MinimalWebView.kt:142-143) and never look at the keys left over; the one key warning is for a key added after creation (MinimalWebView.swift:453-454; .kt:292-293); native-hooks.md:38-42 and types.ts:295-299 say nothing. The usual causes, an extension whose native module isn't linked or an app not rebuilt, and a typo, all look like "the hook does nothing". Q2. **simplify**: at creation, a `core.warning` per enabled key with no hook ("no hook is registered under `x`: is its module linked and the app rebuilt?"), 2-3 lines per platform; on Android only when `hookKeys` is first set, not again after a crash. S, high. Breaks: nothing. (hooks-mechanism #2, its open part)

**B2-04 Three hooks differences are accidental, not platform-made.** (a) `activity` is on Kotlin's context only (Hooks.kt:72, 111), in no doc, used by no hook (the core uses the view's own, requests/FullscreenVideo.kt:40, 86); a hook's own Expo module has `appContext.currentActivity`, and on iOS the core finds its presenter from the view's window (MinimalWebView+Dialogs.swift:84-85), which a hook can do from `webView.window`. (b) Kotlin's detach closure takes `End` (Hooks.kt:31, 47; MinimalWebView.kt:274-277), Swift's nothing (Hooks.swift:14, 28). On Android `onDocumentEnd` always runs just before detach with the same reason (`document.end(CRASHED)` then `detachHooks()`, MinimalWebView.kt:360-361; `CLOSING`, :413-414; the hooks' registrant, :138), so the parameter repeats it, and shared hook code differs in shape. (c) An `ask` through a context whose view has closed is never answered on Android: `HookContext` holds the view (Hooks.kt:107, 121-122) and `askWithId` still registers after `destroy()` (MinimalWebView.kt:308-312, 409-418); iOS answers nil only once the view is deallocated (Hooks.swift:107), not between `invalidate` and dealloc. Q2. **delete**: `activity` from `WebViewContext` (2 lines; a hook writes `appContext.currentActivity`), Kotlin's detach to `() -> Unit` (−3 lines; a hook that needs crash vs close keeps the last `onDocumentEnd` reason, +1 line); answer null once closed (1 line each). S, medium (taste on a and b). Breaks: a hook that reads `context.activity` or takes a detach reason (the sample does neither, SampleExtensionModule.kt:19-40); native-hooks.md:26, 67. (A4-06)

**B2-05 native-hooks.md names neither `uiDelegates` nor `chromeClients`, and lists no platform differences.** Neither name (nor `activity`) is in any doc; native-hooks.md:43-49 says "delegates and clients", page-requests.md:13 only points at the sample. A dialog, permission or fullscreen hook needs exactly those lists. Q2. **document**: one line naming both pairs, and a "Platform differences" list of the five that follow the platforms: the list pairs (Swift's re-assign the delegate on set, MinimalWebView.swift:464-480); `webViewClass` vs `webViewFactory` (Hooks.swift:9; Hooks.kt:26); `configure` gets the configuration (iOS) or the new WebView (Android); `End` is `.committed` vs `COMMITTED`, which a shared hook maps (SampleExtensionModule.swift:19; .kt:27); after a crash iOS keeps the WKWebView and the context, Android attaches again on a new one (already at :67-69). With B2-04 done, that is the whole list. S, high. Breaks: nothing. (A4-04, A4-06)

**B2-06 The crash guard's reset is wrong for Android in two docs.** props.md:18 and glossary.md:48-49: reloads stop "until the next `source` change or `reload()`". Android clears it in `retry()` only (MinimalWebView.kt:232-239; `loadNewSource`, :197-203, doesn't); iOS on both (MinimalWebView.swift:128-129, 193-194). CHANGELOG.md:44-45 has it right. Q2. **document**: name the split in both. S, high. Breaks: nothing. (A4-01)

**B2-07 Android's public native API is wider than the hooks API; iOS's isn't.** Kotlin `class MinimalWebView` is public (MinimalWebView.kt:31) with public `clients`, `chromeClients`, `activity` (:83-85), `emit`, `ask` (:301-305); so are `object NavigationRules` (NavigationRules.kt:4) and `WebViewSource`/`InjectedScript` (MinimalWebViewModule.kt:204, 212). On iOS all are internal (MinimalWebView.swift:4; NavigationRules.swift:4; MinimalWebViewModule.swift:98, 106). The public unprefixed `emit`/`ask` go around the reserved `core` key (Hooks.kt:50), and a `core.*` name that isn't a page request falls through to `onHookEvent` (WebView.tsx:321-326). Q2, Q5. **simplify**: `internal` on the class (or those members) and the types, about 6 modifiers; Expo builds views and records by reflection, which JVM-public bytecode of internal classes allows (check with the build). S, medium. Breaks: code outside the package that reaches into `MinimalWebView` (none documented; the sample imports only `MinimalWebViewHooks`, `WebViewContext`, `DocumentScope`).

**B2-08 Seven one-sentence doc gaps, each confirmed at HEAD.** (1) `didCrash` is always true on iOS (MinimalWebView.swift:421, 434); types.ts:98 and props.md:18 don't say (A4-07, api-surface F10). (2) types.ts:256-257: the rebuild waits for "the background"; it waits for the background or a detached view (`canRecover`, MinimalWebView.kt:380), as props.md:32-33 says (A4-09). (3) navigation-rules.md:37 and migrating-from-react-native-webview.md:211: "`onNavigation` reports every decision"; a hook-decided one isn't (types.ts:61-62; MinimalWebViewClients.kt:109-110) (A4-10). (4) props.md:23-25's ref methods omit `hook` (A4-12). (5) An invalid per-call `timeoutMs` rejects a plain `RangeError` (endpoint.ts:57-58), where bridge.md:39-40 and types.ts:148-150 say a `BridgeCallError`; bridge.md:68 "the same four methods" leaves out the internal `__receive` (pageClient.ts:60) (A4-13). (6) An equal `source` set again doesn't load (MinimalWebView.swift:126; MinimalWebView.kt:199), so a Home button that sets the first `source` back after in-page navigation does nothing; props.md:5 and types.ts:14-23 don't say (api-surface F5, open). (7) native-hooks.md:58 "a number as Double or Int (Kotlin)": `options` and ask answers come through Expo's map conversion (MinimalWebViewModule.kt:115, 144), `handle` args through org.json (:152, 184-189), so one JS `3` can arrive as `3.0` in one and `3` in the other; say which. Q2. **document**. S, high (medium on 7: read from the converters, not run). Breaks: nothing.

**B2-11 A plain `WebViewClient` that overrides a deprecated variant is skipped, silently.** `overrides` looks through a variant only for `WebViewClientCompat` (Hooks.kt:151-164, 175-181), so a plain client's `shouldOverrideUrlLoading(WebView, String)`, `shouldInterceptRequest(WebView, String)` or `onReceivedError(WebView, Int, String, String)` counts as not overriding and the core decides, although calling the modern method on it would reach the override (the platform default forwards). native-hooks.md:49-51 names the Compat variants only; HooksTest.kt covers Compat only. Clients ported from react-native-webview-era code have this shape. Q2. **simplify**: the variant table for every base, 3 entries, plus one HooksTest case; or one doc sentence. S, medium (the forwarding is AOSP's, not run here). Breaks: a hook's deprecated override starts being called. (hooks-mechanism #6)

**B2-12 iOS `call` can't carry an `HTTPCookie`, so iOS cookies from JS still need native code.** `MRWJsonable` turns an unknown object into null (MRWInvoke.m:20-38; documented, platform-settings.md:106) and `MRWObject` knows only `set`/`date`/`data` (:41-49), so `call('httpCookieStore.getAllCookies:', [], { completion: 'value' })` resolves nulls; Android has `cookieManager.getCookie` through `call`. Consumer cost today: an Expo module (module config, podspec, ~15 Swift lines of a hook `handle` over `webView.configuration.websiteDataStore.httpCookieStore`, a JS wrapper, a native rebuild). Q2 (one way on both platforms). **add-seam**: `HTTPCookie` → `properties` in `MRWJsonable`, `{ cookie: {...} }` → `HTTPCookie(properties:)` in `MRWObject`, ~6 lines and a doc line. S, medium (demand). Breaks: nothing. (extension-gaps #7)

**B2-13 A hand-made `Bridge` type-checks and injects nothing.** `Bridge` is structural (types.ts:139-164); `WebView` reads a symbol only `createBridge` sets (WebView.tsx:294-295; createBridge.ts:23, 152). Q2. **simplify**: a `__DEV__` warning when `bridge` is set without it (1 line, also catches untyped JS), or a brand (2 lines). S, medium. Breaks: `Bridge` test doubles (none in src/__tests__). (A4-14, api-surface F6)

Q2. **document** (the glossary names `HookEvent` as the hybrid, the download result, and the takeover shape); optionally rename `hook_not_handled` to `not_found` (breaking: MinimalWebViewModule.swift:60, .kt:150, types.ts:257/260/393, props.md:38, native-hooks.md:56, harness.ts:2185-2186). S, medium (taste). (A4-08)

**B2-15 The sample, native-hooks.md:6's "complete one", breaks the doc's own advice.** Unprefixed keys `pageCounter`, `hookAuth`, `hookDialogs` (SampleExtensionModule.swift:10, 24, 28; .kt:19, 33, 37) against native-hooks.md:36-37; no `ask` or `url`, and `configure` on iOS only (A3 F7); iOS emits `documentEnd` for `closing` too (.swift:19) where Kotlin filters it (.kt:26-27) and the TS type leaves it out (sample src/index.ts:14).
